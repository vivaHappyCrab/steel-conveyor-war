# R21 — Декомпозиция SfmlPlaySession / HudOverlay

**Severity:** Medium · **Домен:** maintainability / testability · **Roadmap:** P2
**Статус валидации:** ✅ Подтверждено по коду (размеры — приближённо)

## Проблема
Декомпозиция SFML улучшена (`SfmlGameRunner` — тонкий composition facade), но `SfmlPlaySession` и `HudOverlay` остаются крупными: один большой `Run` с обработчиками событий/состоянием/циклом. Input command mapping и state-переходы трудно unit-тестировать без окна.

## Где в коде
- `src/SteelConveyorWar.Sfml/SfmlPlaySession.cs` — ~998 непустых строк (в отчёте ~1108 с учётом пустых); один `Run` с event handlers/state/loop.
- `src/SteelConveyorWar.Sfml/Ui/HudOverlay.cs` — ~805 непустых строк (в отчёте ~901).

## План фикса
1. Выделить чистый `InputCommandMapper`: (событие ввода + selection/mode) → команда (DTO), без побочных эффектов — легко unit-тестируется. Согласовать с R2 (sink).
2. Выделить `SessionState`/state-machine (build menu open, overlay open, selection) в отдельный тип с явными переходами.
3. Игровой цикл (`Run`) оставить тонким: pump events → mapper → sink → advance → render.
4. `HudOverlay` разбить на подпанели/модели (часть моделей уже есть: `HudModel`-подобные) и вынести чтение состояния в snapshot (R27).

## Тесты
- Unit-тесты `InputCommandMapper` без окна: ввод → ожидаемая команда.
- Unit-тесты state-machine переходов.

## Definition of Done
- Input-mapping и state-переходы покрыты unit-тестами без создания окна SFML.

## Связанные замечания
R2, R6, R27, R30.

## Статус реализации: ⏸️ Отложено 2026-08-11 (по решению пользователя)

**Почему отложено (а не реализовано вслепую):**
- Это **крупный рефакторинг двух больших файлов** — `SfmlPlaySession.cs` (~998 непустых строк, один монолитный `Run` с event-loop/state/handlers) и `Ui/HudOverlay.cs` (~805 строк). Задача — выделить чистый `InputCommandMapper`, отдельную state-machine (`SessionState`), оставить `Run` тонким и разбить `HudOverlay` на подпанели.
- **Roadmap этого пункта — P2** (в заголовке плана), т.е. ниже приоритетом, чем реализованные P1-исправления.
- **Высокий риск «тихой» регрессии ввода:** воспроизвести всю семантику маппинга «событие ввода + selection/mode → команда» и переходов build-menu/overlay/selection побайтово, не имея возможности собрать проект и прогнать игру (VM недоступен), крайне рискованно — ошибка в маппинге ломает управление незаметно для юнит-тестов, покрывающих лишь новый извлечённый код.
- Ценность пункта — **тестируемость/поддерживаемость**, а не корректность симуляции; детерминизм/честность границы им не затрагиваются, поэтому отсрочка не блокирует остальные исправления.

**Что нужно для возврата к задаче:**
1. Извлечь чистый `InputCommandMapper` (без side effects) и покрыть его юнит-тестами «ввод → ожидаемая команда» без окна SFML, сверяясь с текущим `Run` построчно.
2. Вынести `SessionState`/state-machine (build menu / overlay / selection) с явными переходами + юнит-тесты переходов.
3. Свести `Run` к тонкому циклу pump events → mapper → sink → advance → render; `HudOverlay` разбить на подпанели, читающие snapshot (R27).
4. Обязательно собрать (`dotnet build -c Release`) и вручную прогнать сессию, убедившись, что поведение ввода/HUD не изменилось.
