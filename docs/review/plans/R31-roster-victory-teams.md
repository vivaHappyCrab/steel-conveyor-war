# R31 — Победа и стартовый ростер: убрать зашитый 1v1

**Severity:** High (gameplay correctness для >2 игроков) / Medium для текущего MVP · **Домен:** gameplay / integration · **Roadmap:** P1

**Статус валидации:** ✅ Подтверждено по коду

## Проблема
Условие победы считает выживших **игроков**, а не **команды**: при команде из нескольких игроков победа сработает преждевременно (пока в живых один игрок «своей» стороны) или не сработает корректно при союзниках. Дополнительно старт партии зашит под двух игроков (`PlayerId(1)`/`PlayerId(2)`), а рендер использует фиксированную посадку (seat), а не инъекцию из ростера. Итог: движок фактически поддерживает только 1v1, хотя остальная архитектура претендует на общий multiplayer.

## Где в коде
- `src/SteelConveyorWar.Core/Systems/VictorySystem.cs:16-35` — `CheckVictory`: `activePlayers.Count == 1` считает игроков, а не команды/стороны.
- `src/SteelConveyorWar.Core/GameSimulation.cs:1393-1416` — старт партии зашит на `PlayerId(1)` / `PlayerId(2)` (фиксированный ростер из двух).
- `src/SteelConveyorWar.Sfml/Rendering/WorldRenderer.cs:217-250,417-422` — рендер опирается на фиксированный seat, а не на инъектированную посадку из ростера.

## План фикса
1. Ввести понятие team/side (или alliance) в состояние игрока; условие победы формулировать через «осталась одна активная команда», а не «остался один активный игрок».
2. Стартовый ростер задавать данными: список сидов (seat) с назначением player→team, стартовыми позициями и цветами; убрать хардкод `PlayerId(1)/(2)`.
3. Рендер получает посадку/цвета через инъекцию из ростера, а не через фиксированный seat.
4. Для текущего MVP сохранить 1v1 как частный случай ростера (две команды по одному игроку), но без зашитых допущений в коде.

## Тесты
- Тест победы: команда 2v2 — победа объявляется только когда все игроки одной стороны выбыли, а не при первом выбывшем.
- Тест старта: ростер из N сидов создаёт N корректно назначенных игроков/команд без хардкода.
- Тест рендера: цвета/позиции берутся из ростера (смена ростера меняет отрисовку без правки кода).

## Definition of Done
- Победа определяется по командам, а не по числу игроков.
- Стартовый состав и посадка — data-driven (ростер), без зашитого 1v1.

## Связанные замечания
R6 (декомпозиция GameSimulation), R25 (shared host bootstrap), R18 (data-driven).

### Что сделано (ограниченное ядро корректности — победа по командам)
- **`CheckVictory()` теперь считает команды, а не игроков** (`Systems/VictorySystem.cs`): собираем активные команды `activePlayers.Select(p => p.TeamId).Distinct()`; победа объявляется, когда осталась ровно одна активная команда **и** всего команд > 1 (guard против вырожденного одно-командного ростера). Раньше срабатывало по `activePlayers.Count == 1` — преждевременно при союзниках и некорректно для 2v2.
- **Добавлено `public int? WinnerTeamId { get; private set; }`** в `GameSimulation` (объявление рядом с `WinnerId`). `WinnerId` сохранён как «представитель» победившей стороны — игрок с наименьшим `Id.Value` среди выживших (стабильно, детерминированно), чтобы существующие потребители (`HeadlessHostResult`, рендер, 1v1-тесты) и state-hash не менялись.
- **Поведение 1v1 неизменно**: две команды по одному игроку → единственный выживший = его команда побеждает, `WinnerId` = тот же игрок, что и раньше. Детерминированный хеш не затронут (логика победы не хешируется, а WinnerId в 1v1 идентичен прежнему).

### Тесты
- `tests/SteelConveyorWar.Core.Tests/TeamVictoryTests.cs` (новый): (1) 2v2 (команды [1,1,2,2]) — партия **не** заканчивается при первом выбывшем игроке команды 1; заканчивается только когда выбыли **оба** игрока команды 1 → `WinnerTeamId == 2`, `WinnerId == PlayerId(3)` (наименьший id выжившей стороны); (2) 1v1-регресс — гибель командира игрока 1 → побеждает игрок 2, `WinnerId == PlayerId(2)` (контракт 1v1 неизменен). Для 2v2 недостающие сиды (игроки 3/4) получают критическую сущность через `TrySpawnEntityForTests` в позициях, удалённых от врагов (бой не резолвится).

### Отклонения / отложено
- **Data-driven создание игроков — уже выполнено ранее**: `CreateNewGame` строит ростер из `map.Players.OrderBy(p => p.Id).Select(...)` (не зашитый `PlayerId(1)/(2)`), команды берутся из `MapPlayerDefinition.TeamId`. Этот пункт DoD фактически закрыт (подтверждается тестами `AllianceMinimapTests`, где 3-игровой ростер создаётся корректно).
- **⏸️ Геометрия стартовой посадки (`CreateStartingEntities`) и рендер-seat — отложено.** `CreateStartingEntities` (`GameSimulation.cs`) по-прежнему зашит на два сида с зеркальным размещением (`PlayerId(1)` слева, `PlayerId(2)` справа), а `WorldRenderer` использует фиксированный seat. Полный data-driven ростер требует: (а) добавить в схему карты (`MapPlayerDefinition`) стартовую позицию/цвет на сид; (б) переписать геометрию расстановки под N сидов; (в) провести цвета/позиции в рендер. Это ломающее изменение схемы контента, чувствительное к детерминизму (меняет стартовое состояние и state-hash) и не верифицируемое без сборки/прогона. Отложено до возможности собрать проект и прогнать бенчмарки/replay-детерминизм. Ограниченное ядро (победа по командам) доставлено и покрыто прямыми тестами.
- **Набор кросс-командных проверок консервативен**: победа объявляется только при `totalTeams > 1`, чтобы одно-командный (кооп/песочница) ростер не завершался мгновенно.
