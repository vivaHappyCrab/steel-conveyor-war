# R22 — Performance regression gate

**Severity:** Medium · **Домен:** performance / CI · **Roadmap:** P1
**Статус валидации:** ✅ Подтверждено по коду

## Проблема
CI собирает coverage и запускает multi-OS build/tests/smoke (сильная сторона), но нет benchmark-проекта, порогов на tick time/allocations, large-world/large-army сценариев, coverage threshold и property-based тестов сериализатора для всех kinds. Из-за этого все performance-выводы (R7/R15/R16/R17/R33) остаются статическими.

## Где в коде
- `.github/workflows/ci.yml` — build/test/coverage/multi-OS/smoke; benchmark и порогов нет.
- В репозитории отсутствует benchmark-проект (нет BenchmarkDotNet).

## План фикса
1. Создать проект `SteelConveyorWar.Benchmarks` (BenchmarkDotNet) со сценариями из матрицы ревью (idle factory, belts, army move, battle, FoW, power).
2. Добавить измерение tick p50/p95 и alloc/tick; сериализовать результаты.
3. Ввести пороги (threshold) и регрессионный gate: падение при превышении бюджета времени/аллокаций.
4. Добавить property-based тесты сериализатора для всех `SimulationCommandKind` (см. R11).
5. Опционально: coverage threshold в CI.

## Тесты / метрики
- Benchmark-набор запускается локально и (хотя бы вручную/nightly) в CI.
- Property-тесты round-trip по всем командам зелёные.

## Definition of Done
- Есть benchmark-проект с матрицей сценариев и порогами.
- Регрессия производительности детектируется автоматически.

## Связанные замечания
R7, R15, R16, R17, R33 (все требуют benchmark для оценки severity), R11.

---

## Статус реализации: ⏸️ Отложено 2026-08-11 (по решению пользователя)

Не реализовано в текущем проходе. Причина: **DoD этого плана по своей сути требует работающей сборки и прогона бенчмарков**. Пункты плана — создать проект `SteelConveyorWar.Benchmarks` на BenchmarkDotNet, измерить tick p50/p95 и alloc/tick, откалибровать пороги (threshold) и включить регрессионный gate. Пороги невозможно осмысленно задать без реальных замеров на этой машине/рантайме, а сам gate бессмыслен, пока он не может выполниться в CI/локально. Написать «вслепую» цифры порогов — значит зафиксировать произвольные значения, которые почти наверняка окажутся неверными и сломают CI при первом же реальном прогоне.

Поскольку VM недоступна (нельзя ни собрать benchmark-проект, ни выполнить его), калибровка порогов и верификация gate невозможны. Отложено вместе с R17/R18/R20 как задача, чей результат не верифицируем без реального прогона. Часть, которую можно сделать независимо от бенчмарков, — **property-based round-trip тесты сериализатора для всех `SimulationCommandKind` (пункт 4, связан с R11)** — рекомендуется вынести в отдельную bounded-задачу; здесь она не реализована, чтобы не смешивать её с benchmark-инфраструктурой, ради которой план и заведён. Возврат к R22 требует: (1) создать BenchmarkDotNet-проект со сценариями из матрицы ревью, (2) снять реальные p50/p95 и alloc/tick, (3) откалибровать пороги по факту и включить gate, (4) опционально coverage threshold в CI.
